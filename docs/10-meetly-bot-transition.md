Перед включением новых booking writers нужно перевести их вместе с жизненным циклом worker. Нельзя одновременно оставить старые отправки и активировать новый outbox: это создаст дубли и обойдёт общие гарантии. MEETLY_ENABLED не должен выключать общие команды бота/worker.

Ключ текстового изменения настроек основан на public bot id + chat id + message id + action (SHA256). Текстовая команда владельца задаёт абсолютное значение и применяется к актуальному состоянию внутри writer-lock; replay не перечитывает expected_version. API PATCH использует отдельный patch_settings с обязательным expected_version. Для заявок/карточек при подключении нужны сохранённые версии, а не повторное привязывание старого ключа к новой версии после commit.

До live-перехода: сверить legacy pending с неизвестным previous_status, подготовить принятие старых Google events без меток, прогнать миграции на копии/restore, проверить отсутствие двух writers старой и новой версии. Эти шаги ещё не выполнены на сервере.

## Подготовленная сборка runtime (21.10.2026)

`app/services/booking_runtime.py` собирает BookingCommands, GoogleAvailability,
GoogleEventGateway, обе группы адаптеров доставки и OutboxWorker. Один gateway
используется для проверки занятости и синхронизации; один обязательный environment
передаётся командам и доставкам. Создание объекта не запускает worker и не вызывает
Google/Telegram. Runtime подключён к app.main и booking handlers, включение явное.

OwnerGoogleTokens при обращении находит активного пользователя по настроенному
Telegram ID и передаёт его внутренний ID в GoogleTokens. Владелец может впервые
зарегистрироваться после старта процесса. Проверка выполняется заново на каждом
обращении, read-сессия закрывается до сетевого refresh. Это не отменяет необходимости
перевода изменений доступа и Google binding на общий слой.

`start()` допускает повторный/конкурентный вызов без второго worker. `close()`
останавливает получение новых заданий, ждёт текущую доставку (по умолчанию до 35с),
затем отменяет и дожидается задачи. Отмена доставки сохраняет lease для восстановления.
Ошибки worker не скрываются при повторном start/close. app.main наблюдает за
задачей через wait/supervise_transport и останавливает транспорт при её ошибке.
После close можно запустить новый цикл.

Порядок shutdown: прекратить приём/дождаться обработчиков, закрыть runtime,
затем закрыть общий Bot и DB. Runtime не владеет Bot или engine и не закрывает их.
Отмена сетевой операции не гарантирует отмену уже принятого удалённого эффекта;
SMTP в to_thread также может продолжиться после отмены asyncio-задачи.

## Включение и повтор команды

По умолчанию `BOOKING_RUNTIME_ENABLED=false`: новые записи и изменения встреч
недоступны, старого writer fallback больше нет. Это отдельный флаг технического
перехода, не MEETLY_ENABLED. Регистрация/настройки продолжают использовать общий
слой. Для изолированного тестового запуска нужны актуальная схема (head 0011),
`BOOKING_RUNTIME_ENABLED=true` и уникальный стабильный `CALENDAR_ENVIRONMENT`.
Рабочие .env, сервер и master этим коммитом не изменяются. Флаг нельзя включать на
рабочих данных до проверки legacy events, переноса Google binding и восстановления.

`bot_command_inputs` (0011) фиксирует вход/версии перед командой под коротким SQLite
lock. Текстовый ключ = bot id + chat id + message id + action; callback key содержит
Telegram callback id, а карточка — явную версию. Неизвестные старые кнопки без версии
просят обновить список. Причина отказа вводится с сохранённой в FSM версией заявки.
Форма создания хранит версию настроек/UUID; новое редактирование комментария
обновляет ключ формы. FSM остаётся в памяти: после перезапуска незавершённую форму
нужно заполнить заново, но уже принятые команды сохраняют replay в БД.

При retry используются первоначальные версии и ID конкретного предложения переноса,
даже если операция завершилась/ресурс изменился. Неуспешная операция также сохраняет
снимок: для нового состояния требуется новое сообщение/форма. BotCommandInput и
OperationResult должны сохраняться вместе; автоматическая очистка пока отсутствует.

## Общий подбор времени (21.10.2026)

`AvailabilityQueries` выдаёт дни с количеством слотов и интервалы выбранного дня.
Один запрос ограничен 31 календарным днём; бот листает горизонт записи страницами,
включая случай, когда первая страница полностью занята. Результат содержит только
даты/интервалы, версию настроек и checked_at, без данных чужих встреч.

`booking_policy` используется и превью, и BookingCommands: пересечение полных
интервалов, один buffer между ними, активные резервы, дневной лимит, notice/horizon,
расписание (включая выходные), объединение окон и часовая сетка от начала окна.
Выключенные правила не заменяются стандартным графиком; без правил остаётся Пн–Пт
10–18 МСК. При переносе длительность берётся из встречи, её собственный интервал
исключается, текущее время повторно не предлагается. Владение встречей проверяется
до Google; исключение Google применяется только к конкретному event ID.

Read-сессии используют явный SQLite BEGIN для согласованного снимка и закрываются
до внешнего запроса. После Google повторно проверяются доступ, профиль, расписание,
встреча и локальная занятость. Изменившиеся настройки с переданной версией дают
STALE_VERSION; изменения без увеличения версии/расписания приводят к повторной
проверке (до двух попыток). Внешний snapshot старше 5с не используется. Полностью
закрытые локально дни возвращаются без запроса Google: внешние данные не могут
сделать их свободными. Чтение не создаёт резерв, аудит, команду или уведомление.

Доступность может измениться после показа: выбор времени и окончательная команда
проверяют её снова. Ошибка обязательного Google выводится безопасно, без подмены
пустым успешным результатом и без текста внешнего исключения.

Следующая работа: live-проверка legacy adoption и миграции/restore в изолированном
серверном окружении; затем API/auth. Полного live-перехода пока нет.

## Управляемое Google-подключение (22.10.2026)

Выбор календаря фиксирует OwnerProfile.version до list_calendars и сохраняет
его в FSM. select_calendar проверяет актуальность под SQLite writer-lock,
увеличивает version при изменении ID и сохраняет результат/аудит атомарно.
Повтор ключа возвращает исходный результат, не возвращая старый календарь.
Старые формы без версии требуют заново открыть выбор календаря.
Список использует GoogleTokens: refresh выполняется без открытой DB-сессии.

Политика перехода консервативная: новый calendar ID или другой Google email
запрещены при любой CalendarSync, любой Google outbox, legacy google_event_id
или неотменённой встрече. Историческая sync тоже удерживает binding.
Очередь и event IDs не переписываются. Повторный выбор того же календаря
и reconnect того же email разрешены. Перенос существующих событий между
календарями/аккаунтами — отдельная, пока не реализованная процедура.
Это не автоматическая миграция и не legacy adoption.

begin_oauth сохраняет state без отключения активных токенов. Callback проверяет
активного владельца по настроенному Telegram ID и точное совпадение state
до exchange/userinfo. Сессия закрывается до сети. Перед записью токенов
те же проверки и версия профиля повторяются в короткой writer-транзакции.
Новый flow заменяет предыдущий state; старый callback не может завершить
или испортить новый. Повтор уже завершённого callback отклоняется до сети.

Успешный reconnect увеличивает version. Если разрешена смена аккаунта,
calendar_id сбрасывается, старый refresh token не наследуется. Для того же
email допускается сохранение прежнего refresh token; при неизвестном прежнем
email и существующих встречах смена требует отдельного разбора.
Сравнение аккаунтов основано на email userinfo, отдельный Google subject
в текущей схеме не хранится.

Ошибка или отказ OAuth очищает только совпадающий pending state, сохраняет
активное подключение и записывает фиксированный код. Provider exception,
code/state и токены не попадают в аудит/результаты/тексты ошибок. OAuth-секреты
сохраняются только в OAuthCredential. Новых миграций схемы нет.
Уведомление о завершении OAuth остаётся best-effort Telegram, отдельно от
durable booking outbox. Live Google и рабочий сервер этим изменением не проверены.
