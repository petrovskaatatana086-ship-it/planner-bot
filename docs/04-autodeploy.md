# Автоматическое обновление бота из GitHub

Репозиторий: [pomoshchnik-naznacheniya-vstrechi](https://github.com/petrovskaatatana086-ship-it/pomoshchnik-naznacheniya-vstrechi).
Рабочая ветка: **master**. Сервер: `85.198.65.229`.

Файлы подготовлены. Автообновление включается отдельной настройкой `CALENDAR_AUTODEPLOY_ENABLED=true`; до этого GitHub выполняет только тесты. Установка серверного обработчика сама по себе не перезапускает работающего бота.

## Алгоритм каждого обновления

1. Вы или разработчик отправляете изменения в `master` командой `git push meetings master`.
2. GitHub Actions устанавливает зависимости и запускает тесты. При ошибке сервер не получает новую версию. Для pull request выполняются только проверки.
3. Если автообновление включено, GitHub собирает Linux/Docker-образ, помеченный полным SHA коммита. Сборка не расходует оперативную память вашего VPS.
4. Перед доставкой workflow проверяет, что коммит всё ещё последний в `master`. При нескольких быстрых push промежуточные ожидающие релизы могут быть пропущены; доставляется свежая версия.
5. Образ сжимается и передаётся по SSH. Сверяется заранее сохранённый публичный ключ сервера. На сервере не нужны доступ к GitHub, GitHub-токен или пароль от реестра образов.
6. Серверный обработчик проверяет размер архива, имя образа, SHA и архитектуру. До завершения этих проверок текущий бот продолжает работать.
7. Обработчик сохраняет предыдущий образ, останавливает только `calendar-bot/bot` и делает согласованную SQLite-копию. Бот кратковременно недоступен во время переключения.
8. Одноразовый контейнер выполняет миграции. Затем запускается новый контейнер и проверяются его Docker healthcheck, локальный `/health` и публичный HTTPS `/health`.
9. Проверяются контрольные суммы конфигов nginx и существующих сервисов. Записываются SHA новой версии и данные предыдущего образа. Удаляется загруженный архив; сохраняются текущий и предыдущий образы и исходный `:production`. После успешных обновлений сохраняются последние 14 журналов/снимков развёртывания.
10. В GitHub Actions появляется зелёный результат или причина ошибки. Одновременно обновлять бота не позволят очередь Actions и серверная блокировка.

`.env`, Google-токены, встречи и заявки не копируются с компьютера и не заменяются файлами из GitHub. Используется текущая серверная база `/opt/calendar-bot/data/planner.db`. Режим приёма Telegram-обновлений задаётся через `BOT_MODE` в серверном `.env`; CI сохраняет этот выбор. Настройка webhook описана в [инструкции размещения](../deploy/README.md#webhook-и-polling).

## Что вам нужно сделать один раз — рекомендуемый способ

### 1. Откройте PowerShell в папке проекта

```powershell
Set-Location -LiteralPath 'C:\Users\sukhorukov.da\My Projects\Планировщик задач_БОТ'
gh auth status
```

Должен быть выбран аккаунт `petrovskaatatana086-ship-it`. Если входа нет, выполните `gh auth login` и войдите в этот аккаунт. GitHub CLI (`gh`) и OpenSSH уже использовались для данного проекта. Для другого компьютера сначала потребуются они, Python и ваш действующий административный SSH-ключ.

### 2. Запустите однократную настройку

```powershell
.\.venv\Scripts\python.exe deploy\autodeploy\setup.py --install-server --configure-github
```

Скрипт самостоятельно:

- создаст отдельный SSH-ключ `C:\Users\sukhorukov.da\.ssh\calendar_bot_github_actions` без изменения вашего административного ключа;
- подключится к серверу как `tataynka_pe` по уже имеющемуся административному ключу;
- создаст пользователя `calendar-deploy`, установит ограниченный обработчик и проверит, что новый ключ не может открыть обычную shell-сессию;
- передаст приватную часть нового ключа в секрет **этого репозитория** `CALENDAR_DEPLOY_SSH_KEY` через GitHub CLI, не выводя её в терминал;
- включит переменную репозитория `CALENDAR_AUTODEPLOY_ENABLED=true`.

Дождитесь сообщений `Server installed; deployment key restriction verified` и `automatic deployments enabled`. Если возникла ошибка, не отправляйте в чат ключ или `.env`: пришлите только текст ошибки. Повторный запуск использует уже созданный ключ.

### 3. Выполните первое обновление вручную из GitHub

Откройте [Actions](https://github.com/petrovskaatatana086-ship-it/pomoshchnik-naznacheniya-vstrechi/actions) → **Test and deploy calendar bot** → **Run workflow** → ветка **master** → **Run workflow**.

Альтернатива той же операции в PowerShell:

```powershell
gh workflow run deploy.yml --repo petrovskaatatana086-ship-it/pomoshchnik-naznacheniya-vstrechi --ref master
```

Дождитесь зелёных заданий **test** и **deploy**, откройте [проверку состояния бота](https://calendar.tatyana-petrovskaya.ru/health) — ожидается `{"status":"ok"}` — и проверьте меню бота в Telegram. После этого каждый следующий push в `master` запускает обновление самостоятельно.

Если GitHub предлагает разрешить Actions, включите их для репозитория в **Settings → Actions → General**. Используются официальные `actions/checkout` и `actions/setup-python`, закреплённые по полным SHA; сторонний action для SSH не нужен. Для запуска должны быть доступны минуты/лимиты GitHub Actions вашего аккаунта.

## Если не хотите настраивать GitHub через командную строку

Сначала выполните только серверную часть:

```powershell
.\.venv\Scripts\python.exe deploy\autodeploy\setup.py --install-server
```

Затем в репозитории откройте **Settings → Secrets and variables → Actions**:

1. Вкладка **Secrets → New repository secret**: имя `CALENDAR_DEPLOY_SSH_KEY`, значение — всё содержимое созданного приватного файла, включая строки `BEGIN OPENSSH PRIVATE KEY` и `END OPENSSH PRIVATE KEY`.
2. Вкладка **Variables → New repository variable**: имя `CALENDAR_AUTODEPLOY_ENABLED`, значение `true`.
3. Выполните первое обновление через **Actions → Run workflow**, как описано выше.

Это отдельный технический ключ, не ваш личный административный ключ. Он должен попадать только в GitHub Actions secret данного репозитория. Публичный файл с окончанием `.pub` в поле секрета не подходит.

## Что именно появится на сервере

- Пользователь `calendar-deploy` без обычного интерактивного входа по этому ключу, без членства в группах `sudo` и `docker`.
- `/usr/local/libexec/calendar-bot-ssh` — разрешает только одну команду с проверенным SHA.
- `/usr/local/sbin/calendar-bot-deploy` — root-owned обработчик; единственная sudo-команда, доступная этому пользователю.
- `/etc/calendar-bot/compose.yml` — root-owned конфигурация запуска.
- `/var/lib/calendar-bot-deploy` — блокировка, журналы, снимки БД и `current.json` с последним успешным релизом.

Обработчик обновляет только Docker-проект `calendar-bot`, сервис `bot`, с портом `127.0.0.1:8012`, прежним каталогом данных и лимитом RAM 256 МБ. Он не редактирует nginx, сертификаты, firewall, `planner`, `counterparty-check` и каталоги других сайтов. Контейнер не получает Docker socket или root-доступ к серверу.

CI доставляет **образ приложения**, а не исходники в `/opt/calendar-bot/app`. Этот каталог остаётся копией прежней ручной установки. Номер действующего релиза смотрите в `/opt/calendar-bot/REVISION` или `current.json`. После включения CI обычные обновления выполняйте через GitHub; ручная сборка из старого серверного каталога вернёт старые исходники.

Изменения привилегированного обработчика, серверного Compose, nginx или конфигурации webhook устанавливаются отдельно администратором после проверки; отправка их в GitHub сама по себе не изменяет хост. Для обновления подготовленных серверных скриптов повторно используется `setup.py --install-server` после завершения текущего релиза.

## Если обновление не удалось

- **Тесты, сборка, доставка или проверка архива не прошли:** действующий бот продолжает работать.
- **Не прошла миграция до запуска нового бота:** восстанавливаются снимок БД и предыдущий образ.
- **Новая версия не прошла healthcheck, схема БД не менялась:** возвращается предыдущий образ; текущая база сохраняется, чтобы не потерять заявки, которые могли поступить за это время.
- **Схема БД изменилась, новая версия могла уже принять заявки и затем не прошла проверку:** кандидат останавливается, БД сохраняется; workflow сообщает `Manual recovery required`. Автоматически стирать новые заявки старым снимком нельзя. Нужна проверка совместимости предыдущей версии или исправляющий релиз. Необратимые изменения схемы требуют отдельного плана миграции.

Логи падения доступны администратору в `/var/lib/calendar-bot-deploy/<попытка>/commands.log` и `failure.txt`; они не публикуются целиком в GitHub Actions. В этой папке лежит соответствующий снимок `before.sqlite3`. Ежедневные резервные копии в `/var/backups/calendar-bot` продолжают создаваться независимо от CI.

Успешный healthcheck подтверждает запуск HTTP-сервера приложения. Он не заменяет ручную проверку бизнес-сценария при существенных изменениях. Пока используется `MemoryStorage`, перезапуск сбрасывает незавершённые шаги диалога; сохранённые заявки и встречи остаются в SQLite.

## Как приостановить автообновления

В GitHub откройте **Settings → Secrets and variables → Actions → Variables** и установите `CALENDAR_AUTODEPLOY_ENABLED=false`. Уже начавшееся развёртывание лучше дождаться до завершения.

Это отключает последующие доставки и не останавливает работающего бота. Тесты после push продолжают запускаться. Для включения верните `true`.

## Ручной возврат предыдущего образа

Это команда для администратора при подтверждённой совместимости схемы БД. Она не восстанавливает старый снимок базы и не вызывает глобальный Docker prune.

```sh
sudo cat /var/lib/calendar-bot-deploy/current.json
# Скопировать previous_image из этого файла вместо ИМЯ_ПРЕДЫДУЩЕГО_ОБРАЗА:
sudo env CALENDAR_IMAGE=ИМЯ_ПРЕДЫДУЩЕГО_ОБРАЗА docker compose \
  --project-name calendar-bot --project-directory /opt/calendar-bot \
  -f /etc/calendar-bot/compose.yml up -d --no-deps --no-build --pull never --wait bot
```

Предпочтительный способ исправления кода — `git revert` ошибочного коммита и новый push в `master`: он снова проходит проверки и фиксирует возврат в истории.
