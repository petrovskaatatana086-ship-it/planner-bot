# Meetly — техническое проектирование

Статус: завершено 20.10.2026. Это контракт будущей реализации, а не описание работающего API. Связанные документы: [ТЗ](06-meetly-mini-app-spec.md), [журнал](07-meetly-progress.md), [API](09-meetly-api-contract.md), [изоляция](05-project-isolation.md).

## 1. Архитектура

Первый выпуск: Python 3.12, aiogram 3, существующий aiohttp, SQLAlchemy 2, Alembic, SQLite/aiosqlite и HTML/CSS/JS без сборщика. Один процесс обслуживает бот, `/meetly/`, `/api/meetly/v1/`, OAuth callback и worker интеграций. Одна база и общая бизнес-логика; отдельный API-контейнер, Redis и PostgreSQL не требуются. Прежнее намерение перейти на PostgreSQL в technologies.md не описывает текущий production-шаблон: compose.production.yml задаёт SQLite `/data/planner.db`. Live VPS на этом этапе не проверялся.

Nginx завершает HTTPS; клиент и API имеют один origin, CORS закрыт. Рабочие статические файлы отделяются от демонстрации, переключатель ролей и вымышленные данные в production не публикуются. Запуск — inline web_app в личном чате, с подписанными данными пользователя; reply keyboard/sendData не используется как протокол входа.

`MEETLY_ENABLED=false` по умолчанию выключает кнопку, статику и API (404), сохраняя общую логику бота и worker. Отдельный `BOOKING_MUTATIONS_ENABLED` при обслуживании запрещает новые изменения расписания в обоих интерфейсах; очередь уже принятых действий продолжает работу. OwnerProfile.booking_enabled запрещает новые заявки и запросы переноса, но сохраняет просмотр, отмену и решения по принятым заявкам.

Тестовый сервис: Compose-проект meetly-test, `/opt/meetly-test`, отдельные сеть, data, бот, токены, Google-календарь и HTTPS origin. Предлагаемый `meetly-test.tatyana-petrovskaya.ru` не считается созданным. Порт выделяется после проверки; исходный бюджет 256 МиБ/0.5 CPU требует проверки текущих ресурсов VPS. Production остаётся calendar-bot, без второй копии его токена или SQLite.

## 2. Общие сервисы

- domain/booking.py: чистые функции времени, интервалов, ограничений и переходов.
- services/booking.py (новый): команды регистрации, записи, решений, переноса, отмены, настроек; одна транзакция на команду.
- services/availability.py (новый): общая локальная и внешняя занятость.
- db/repositories.py: SQL без commit и сетевых вызовов.
- app/meetly/ (новый): маршруты, DTO, авторизация; HTTP не вызывает handlers через искусственный Message.
- services/outbox.py (новый): долговечные задания Google/Telegram/SMTP; старые прямые отправки из обработчиков удаляются при переводе на сервис.

Сервис получает доверенного actor, command_id, expected_version, данные и clock. Проверки прав, состояния и ограничений выполняются в сервисе. Все writer-пути бота переводятся на него до включения API.

## 3. Статусы и резервы

| Сущность | Переходы | Занятость |
| --- | --- | --- |
| BookingRequest | pending → approved/rejected | Только pending с reserved_until > now |
| BookingRequest approved | Исходное решение сохраняется после отмены/переноса встречи | Не блокирует, источник — Meeting |
| Meeting | confirmed/rescheduled → reschedule_pending | Старое время продолжает блокировать |
| Ожидающий перенос | Одобрение → rescheduled; отказ → прежнее активное состояние | Предложенное время не резервируется |
| Активная Meeting | → cancelled_by_client/cancelled_by_owner | После commit локальное время освобождается |

Новая заявка резервирует время на 30 минут. Истечение не отклоняет заявку: она остаётся pending во входящих, reservation_active вычисляется при чтении. При now=reserved_until резерв уже не действует. Legacy pending с NULL reserved_until не резервирует время. Повтор команды не продлевает резерв. При одобрении проверяется доступность, исключая собственный резерв; при конфликте заявка остаётся pending.

Перенос проверяет новый слот при запросе и согласовании. До решения старое время сохраняется, новое может занять другой клиент. Второй pending-перенос одной встречи запрещён. Отмена закрывает перенос атомарно; перенос администратором закрывает его как superseded. То же время не принимается. Отказ сохраняет исходный confirmed/rescheduled, интервал и причину решения в структурированной истории.

Счётчики считают исходные BookingRequest за всю историю; переносы — отдельно. Отмена встречи не меняет approved. Legacy withdrawn входит в total и additional.withdrawn: при таких записях сумма трёх основных статусов может отличаться от total. Отзыв pending не входит в первую версию. Завершённость встречи вычисляется по end_at <= now; завершённые встречи не изменяются. История включает отмены и отклонённые заявки.

## 4. Время и доступность

API принимает RFC3339 только с offset, хранение/сравнение — UTC, показ — Europe/Moscow («МСК»). Наивные datetime, прочитанные из существующей SQLite, трактуются как UTC. Даты диапазонов — московские. Часовой пояс устройства не влияет на выбор времени.

Длительность новой заявки фиксируется из профиля при создании; встреча и её перенос сохраняют end_at-start_at. Текущее использование новой default_duration при переносе в handler необходимо заменить согласно ТЗ. Настройки не переписывают существующие интервалы.

Расписание берётся из активных ScheduleRule. Если правил вообще нет — fallback Пн–Пт 10:00–18:00; только неактивные правила означают отсутствие рабочего времени. Пересекающиеся диапазоны объединяются. Сетка начал остаётся часовой от начала рабочего диапазона, как в текущем domain. Встреча целиком помещается в диапазон; перерыв после последней встречи может выходить за конец дня.

Интервалы полуоткрытые. Две встречи совместимы, если `a.end + buffer <= b.start` либо наоборот. Перерыв применяется один раз между интервалами; берётся текущая настройка. При buffer=0 допускается стык. Изменение buffer не отменяет существующие встречи, но влияет на новые действия. Внешняя занятость проверяется тем же способом. При переносе исключается только собственная встреча по ID, а не все записи с тем же началом.

Горизонт: от московской текущей даты до now.date+horizon включительно. Новая заявка/предложение переноса: начало >= now+notice. Отмена клиентом: текущее начало >= now+notice. Администратор отменяет будущую встречу без клиентского срока; переносит в доступный слот с notice и расписанием. При одобрении ранее поданной заявки сохраняется длительность и требуется будущее начало; истечение notice после подачи само по себе не запрещает одобрение.

Дневной лимит считает активные встречи и живые резервы по московской дате начала, без approved-дублей. При переносе текущая встреча исключается из лимита целевого дня. Предложения переноса лимит не занимают. Одобрение заявки также перепроверяет лимит. Снижение лимита не удаляет существующие записи.

Настройки совпадают с диапазонами команд бота: duration 15–240 мин, buffer 0–120, daily_limit 1–50, horizon 1–180 дней, notice 1–720 часов, booking_enabled boolean. Только целые значения, bool не принимается вместо integer.

## 5. SQLite и конкуренция

Файл на локальном диске, без NFS. Соединения: foreign_keys=ON, busy_timeout=5000; WAL включается контролируемо при подготовке окружения. Все команды изменения расписания и настроек используют BEGIN IMMEDIATE первой SQL-командой новой сессии, до SELECT; нельзя начинать его поверх SQLAlchemy autobegin.

Порядок:

1. Вне write-транзакции получить Google busy, если календарь подключён. Максимальный возраст снимка в момент проверки — 5 секунд.
2. BEGIN IMMEDIATE; заново прочитать actor, профиль, состояние, version и результат команды. При смене версии профиля/calendar binding или устаревшем снимке освободить транзакцию и повторить получение снаружи, максимум два прохода.
3. Зафиксировать единое now, проверить локальные интервалы, резервы, лимит, права и переход. Атомарно записать сущности, version+1, аудит, результат команды и outbox.
4. Commit, затем ответ. Сетевые запросы не удерживают write-lock.

SQLite сериализует писателей файла, включая разные процессы. asyncio.Lock не является защитой БД. SQLITE_BUSY: rollback и до двух повторов всей команды с тем же ключом; затем 503 DATABASE_BUSY/Retry-After. Иные ошибки автоматически не повторяются. Корректность BEGIN IMMEDIATE с используемыми SQLAlchemy/aiosqlite проверяется двумя независимыми engine на этапе 4.

Google не участвует в транзакции SQLite. Гарантия отсутствия пересечений относится к операциям бота/API. Ручное событие Google, созданное одновременно после проверки, может конфликтовать: сверка помечает calendar_conflict, сообщает владельцу и не удаляет подтверждённую встречу автоматически. При недоступном подключённом календаре — 503 CALENDAR_UNAVAILABLE; при отсутствии подключения — локальные правила и integration_state=not_connected.

Для переноса нельзя вычитать собственный интервал из freeBusy: это скроет чужое пересечение. Использовать events.list с пагинацией/раскрытием повторов и исключением точного google_event_id; учитывать прозрачность, all-day и отменённые события. Недостаток прав чтения, ошибки внутри ответа конкретного календаря и неполные данные означают отказ проверки, а не свободный слот.

## 6. Схема и миграции

Только additive изменения, legacy поля и статусы сохраняются.

| Изменение | Назначение |
| --- | --- |
| version integer NOT NULL default 1 в BookingRequest, Meeting, OwnerProfile | Optimistic concurrency |
| UNIQUE Meeting.booking_request_id | Одна встреча на заявку |
| reschedule_requests | meeting_id, proposed_start/end, comment, reason, previous_status, status pending/approved/rejected/cancelled/superseded, timestamps; partial unique index pending на meeting |
| operation_results | actor_id, command_id, kind, payload_hash, resource_id, response_json, created_at; UNIQUE(actor_id,command_id) |
| outbox | event_id, entity_id/version, channel, kind, state, attempts, next_attempt_at, lease_until, error_code; unique event/channel/kind |
| calendar_sync | meeting_id unique, desired_version, applied_version, state, calendar_id, deterministic_event_id, last_error_code |
| api_sessions | token_hash unique, user_id, expires_at, revoked_at; сырой токен не хранится |
| User.consent_version nullable | Версия текста; старые consent_at продолжают признаваться |

Новые переносы и legacy proposed_* обновляются одной транзакцией. Причина отказа хранится в reschedule_requests, а не извлекается из технического журнала. Аудит содержит actor, действие, ID и безопасный код; персональные тексты не копируются в технические логи.

Preflight резервной копии: duplicate booking_request_id у встреч, orphan FK, неизвестные статусы (включая rescheduled_pending), отрицательные интервалы, неполные proposed_*. При аномалии остановить миграцию с отчётом ID, без автоматического удаления. Корректные ожидающие переносы перенести в новую таблицу; резервы не продлевать. Индексы: status/start/end, reserved_until, outbox state/next_attempt_at. Alembic выполняет один release-шаг до запуска; create_all не заменяет upgrade.

## 7. Идемпотентность

Каждая бизнес-мутация API требует UUID Idempotency-Key, область actor+key. Хеш включает метод, маршрут, нормализованное тело и expected_version. Совпавший ключ/хеш возвращает сохранённый результат, иной payload — 409 IDEMPOTENCY_KEY_REUSED. Порядок: актуальные права → replay → проверка версии. Успешный результат коммитится вместе с сущностью; ошибка до commit не оставляет вечное «выполняется». Ключи команд записи хранятся вместе с историей, без короткого TTL.

Бот использует bot identity/chat/message/action; callback — исходное сообщение с кнопкой/action/entity, а не только callback_query.id. Другой ключ не обходит проверку состояния/уникальность встречи. Команды существующих ресурсов требуют expected_version; HTTP использует If-Match. Новая заявка передаёт settings_version, при изменении настроек требуется обновить слоты.

После сетевого сбоя клиент запрашивает результат по ключу и повторяет исходную команду с тем же ключом. 404 результата не доказывает завершение параллельного запроса. Отдельная таблица блокировок in-memory не требуется.

## 8. Авторизация

POST /session получает initData в Authorization: tma <raw>, выдаёт случайный bearer 256 бит на 60 минут без скользящего продления. Максимум initData 16 КиБ. Строгий query parse, запрет duplicate keys, обязательные hash/auth_date/user, положительный целочисленный user.id. HMAC: secret=HMAC-SHA256(key=WebAppData,message=bot_token), затем digest check-string. Check-string содержит декодированные поля кроме hash, включая signature при наличии, по алфавиту через LF; JSON user не сериализуется заново. Сравнение constant-time. Это bot-token HMAC, его нельзя смешивать с отдельной third-party Ed25519 схемой.

Политика приложения: auth_date не старше 5 минут, допуск будущего 30 секунд. Повтор обмена в окне допустим и ограничен rate limit. После expiry требуется заново открыть mini app; старую initData нельзя обновить изменением auth_date. Токен только в памяти вкладки, сервер хранит SHA256 и UTC expiry; localStorage и URL не используются. DELETE /session отзывает сессию.

Каждый запрос проверяет актуальные status, регистрацию и роль по OWNER_TELEGRAM_ID. Новый клиент имеет доступ только к /me, /consent, /registration и управлению сессией. Регистрация атомарна с consent_at/version и unique telegram_id; существующий профиль при входе не перезаписывается. Чужой ресурс — 404, /admin клиенту — 403.

JSON body до 32 КиБ, неизвестные поля отклоняются. Ответы с персональными данными no-store. Авторизация не через cookie; CORS закрыт, Origin проверяется при наличии. Начальные лимиты: вход 10/мин/IP, чтения 120/мин/actor, мутации 20/мин/actor, ответ 429/Retry-After. Authorization, initData, регистрационные тела не логируются приложением/proxy. CSP допускает own scripts и официальный Telegram script; frame-ancestors проверяется с Telegram Web, чтобы не запретить его встраивание. Пользовательский текст — textContent.

## 9. Интеграции и восстановление

Источник истины — локальный commit. Business status и integration_state pending/synced/failed/not_connected раздельны. UI не обещает обновлённый Google при pending. Уведомление с Meet-ссылкой ждёт её готовности; при длительном сбое отправляется сообщение о решении и задержке ссылки. Google invitation и прикладное письмо — отдельные каналы.

Outbox атомарна с бизнес-событием. Worker берёт задание короткой транзакцией с lease 90 секунд, сеть выполняется вне транзакции с timeout 30 секунд. После падения lease истекает. Для одной встречи одновременно не более одного Google-задания; порядок версий строгий, устаревшие задания сворачиваются к актуальному desired state. Завершение старого задания не помечает новую версию synced. Отмена до create позволяет пропустить создание; create в полёте после завершения догоняется delete.

Event ID Google (UUID hex) и conference requestId сохраняются до запроса и стабильны. Текущий conference requestId не дедуплицирует сам event. После timeout/409 выполнить GET по ID и сверить private extendedProperties meeting/environment; чужое событие не перезаписывать. Legacy события сохраняют старый google_event_id. PATCH повторяет актуальное состояние, после неоднозначного ответа сначала сверяет remote state. DELETE 404/410 означает достигнутую отмену. Meet URL может появиться позже: ограниченный polling, без создания второго события.

Повторы временных ошибок: 5с, 30с, 2м, 10м, 30м, затем failed с ручным повтором того же задания. 429 учитывает Retry-After, 401 допускает один refresh, постоянные 4xx требуют вмешательства. Сохранять error_code, не сырые ответы. Telegram/SMTP дедуплицируются локально, но потеря ответа после приёма может дать повтор: абсолютная exactly-once внешней доставки не гарантируется. SMTP использует стабильный Message-ID для диагностики.

Сверка при старте/каждые 5 минут: lease, pending/failed, desired/applied версии. Ограниченный скан будущих 14 дней выявляет конфликты внешних событий с пагинацией; произвольные события не импортируются в заявки и не удаляются. Ручное изменение managed event помечается conflict для владельца.

## 10. Клиент и API

Маршруты/DTO — в 09-meetly-api-contract.md. allowed_actions сервера управляет UI, но не заменяет повторную проверку команды. Формы сохраняют ввод при конфликте; после действия перечитываются карточка, календарь и счётчики. Обновление при открытии раздела и activated/visibilitychange; WebSocket не нужен. AbortController/sequence предотвращает перезапись нового дня старым ответом. Форматирование всегда Europe/Moscow.

## 11. Тестовое окружение и откат

Сначала fake Google/SMTP/Telegram и временная файловая SQLite без загрузки production .env. Далее отдельный тестовый бот. SMTP — перехватчик или allowlist тестовых получателей; при отсутствии тестового транспорта отправки запрещены. Google — отдельный календарь и environment-specific event IDs. Только синтетические данные. DNS/секреты/HTTPS подготавливаются на этапе 4, реальные доступы в git не сохраняются.

Выпуск двумя версиями: общие команды/миграции/outbox с выключенным Meetly; после проверки бота включение API и кнопки. До выпуска обязательны визуальное согласование, приёмка Android/iOS/Desktop, миграция копии, проверка restore и соседних сервисов. Порт/ресурсы проверяются заново, nginx -t до reload.

Rolling overlap старого и нового writer запрещён. Остановить сервис, сделать согласованную SQLite backup API копию либо копию файлов при остановленном процессе, применить Alembic, запустить один экземпляр. Копия только planner.db при активном WAL недостаточна.

Предпочтительный откат: MEETLY_ENABLED=false, общая логика и worker продолжают работу. Откат образа — только до совместимой версии общего слоя и очереди. Самая старая версия, игнорирующая outbox/version, небезопасна даже при читаемой схеме. Restore — при остановленных writers, с оценкой потери новых операций и сверкой Google; не выполнять автоматический downgrade/restore поверх активной БД.

| SQLite, два независимых engine | Конкурентные заявки/одобрения/переносы: один победитель, нет перекрытий/дублей; rollback/retry SQLITE_BUSY |
| Интервалы | Граница expiry, approved не блокирует старый слот, длительности, buffer, лимит, МСК |
| Статусы | approve против reject; перенос против отмены; отказ сохраняет исходные статус/длительность |
| Идемпотентность | Потеря ответа после commit, replay/другой payload, перезапуск, bot/API |
| Авторизация | HMAC vectors, signature, duplicate keys, старое/будущее auth_date, owner spoof, чужой ID, блокировка после входа |
| Google | Timeout create, 409/404/410, per-calendar errors, чужое пересечение, all-day/recurring, смена binding |
| Outbox | Падения до/после отправки, lease recovery, порядок версий, retries, задержка Meet URL |
| Миграции | Legacy fixture, duplicate/unknown preflight, перенос, backup/restore, выключение Meetly |
| UI | Общий профиль bot/API, пагинация, статистика после отмены, устаревшие ответы, другой TZ устройства, Telegram клиенты |

Этап 4: регрессионные тесты выявленных рисков → additive миграции/транзакции → перевод writer-путей бота/outbox → выключенный API/auth → тестовый запуск. Далее этапы клиентских и административных экранов. Производственное развёртывание остаётся отдельным этапом.
