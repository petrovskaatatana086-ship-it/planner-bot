# Meetly — техническое проектирование

Статус: начата инвентаризация, серверные изменения ещё не внесены.
Дата: 19.10.2026. Связанные документы: `06-meetly-mini-app-spec.md`, `07-meetly-progress.md`.

## Принятые направления

- Использовать существующий aiohttp HTTP-сервер, SQLAlchemy и модели бота. Для первого frontend не требуется сборщик: HTML/CSS/JS достаточны для календаря и форм.
- Макет живёт отдельно в `miniapp/` и не подключён к `app.web`. Демонстрационный выбор роли и локальные записи не попадут в рабочую авторизацию.
- Рабочий API расположить под отдельным префиксом, например `/api/meetly/v1/`. Включение интерфейса и API — явная настройка, по умолчанию выключено.
- Верифицировать Telegram initData на сервере; не доверять initDataUnsafe и выбору роли в браузере. Использовать HTTPS и заголовок авторизации, не параметры URL. Проверять подпись, auth_date, допустимый возраст, структуру и уникальность полей. Не сохранять initData в логах или localStorage.
- Авторизацию сверять с актуальной официальной документацией: https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app (проверена 19.10.2026). Конкретный срок сессии и способ обновления ещё не зафиксированы.
- Роль получать по серверным правилам бота и действующему OWNER_TELEGRAM_ID, блокировки и регистрацию проверять для каждой операции.
- Транзакции и проверки записи выделить в общий слой для Telegram-обработчиков и HTTP. Нельзя вызывать обработчик сообщений с поддельным Message из HTTP API.

## Найденные особенности текущего кода

| Область | Наблюдение | Что сделать до подключения записи |
| --- | --- | --- |
| Авторизация | Бот проверяет пользователя в обработчиках | Вынести серверные проверки доступа в общий слой |
| Слоты | `get_busy_starts` возвращает начала заявок/встреч | Проверять пересечения полных интервалов с длительностью и перерывами, а не только равенство начал |
| Резервы | `reserved_until` устанавливается на 30 минут, но `get_busy_starts` не учитывает его | Описать единый жизненный цикл резерва и обработку истечения, сохранить совместимость обоих интерфейсов |
| Подтверждённая заявка | В занятость входят заявки `approved` и встречи | При переносе/отмене исходная заявка может продолжать занимать прежнее время; воспроизвести отдельным тестом и исправить общей операцией |
| Подтверждение | `approve_booking_request` создаёт встречу без встроенной защиты от повторов | Добавить защиту состояния, идемпотентность и ограничение одной встречи на заявку |
| Перенос | Предложенное время хранится в Meeting | Проверять занятость повторно при согласовании; согласовать резервирование нового времени |
| Интеграции | Google/уведомления вызываются из обработчиков | Определить повторяемые операции, фиксацию результата и восстановление после частичного сбоя |
| История | Клиентские выборки ограничены 10 записями | Добавить явную пагинацию для API |
| Ошибки | Часть ответов бота включает текст исключения | API возвращает безопасный код и сообщение, подробности сохраняются без секретов |

Это результаты чтения кода, а не доказательство воспроизведённых ошибок в production. Нельзя исправлять их незаметно только в новом API: оба интерфейса должны пользоваться одинаковыми правилами.

## Предварительные группы API

- Сессия и профиль: проверка Telegram, роль, статус регистрации, регистрация с согласием.
- Расписание: доступные дни, слоты выбранного дня, текущие ограничения записи и часовой пояс.
- Клиент: собственные заявки и встречи, карточка, новая заявка, запрос переноса, отмена.
- Владелец: календарь диапазона, входящие, подтверждение и отклонение заявки, обработка переноса, перенос и отмена встречи.

Все меняющие операции требуют ключ повторного выполнения. Изменения устаревшей карточки или конкурирующей записи возвращают конфликт с предложением обновить данные. Пагинация и формат ошибок едины для всех выборок.

## Транзакции и интеграции — ещё спроектировать

SQLite не поддерживает PostgreSQL-блокировки интервалов. Один процесс или asyncio.Lock сами по себе не обеспечивают безопасность нескольких процессов и контейнеров. Перед выбором реализации нужно определить реальный DATABASE_URL без вывода секретов и допустимую топологию тестового/рабочего окружения.

Нужны отдельные решения и проверки:

1. Атомарная проверка доступности и фиксация резерва для SQLite; стратегия блокировок и повторов при конкуренции.
2. Уникальность подтверждения заявки и повтор операций с одинаковым ключом.
3. Устойчивое выполнение Google Calendar и уведомлений с записью состояния доставки; не обещать абсолютную однократность email при сетевом сбое после приёма сообщения SMTP-сервером.
4. Совместимые миграции и откат при старом приложении.
5. Отдельные тестовые токен, база, календарь, email-получатели и адрес HTTPS; реальные ключи не коммитить.

## Точка продолжения

После визуального согласования макета закончить контракт статусов/резервов, воспроизвести найденные конфликты тестами, затем реализовать отключённую по умолчанию серверную основу. До этого реальные операции и публикация в production не выполняются.
