# Meetly: принятие старых Google-событий и репетиция миграции

Состояние 22.10.2026. Это инструменты подготовки перехода, не отчёт о выпуске.
Текущий Alembic head — 0011. Новых изменений схемы для принятия событий нет.

## Репетиция миграции и восстановления

Из корня проекта, с установленными зависимостями:

```powershell
.venv/Scripts/python.exe -m deploy.rehearse_migration --database planner.db --workdir .deploy/rehearsal-new
```

Каталог результата должен быть новым. Исходная база открывается только read-only,
копируется через SQLite Backup API, включая зафиксированные данные WAL.
`.env`, настройки приложения и сеть не используются. Alembic получает соединение
с копией явно; обычный запуск Alembic продолжает использовать прежние настройки.
База без alembic_version не размечается автоматически.

Результат в указанном каталоге:

- `before.sqlite3` — согласованный снимок исходной схемы и данных;
- `upgraded.sqlite3` — отдельная копия после настоящего `upgrade head`;
- `restored.sqlite3` — восстановление из снимка до миграции, даже при ошибке upgrade;
- `report.json` — версии, количества строк и безопасные результаты проверок.

Проверяются integrity_check, foreign_key_check, поля актуальной модели, Alembic head,
сохранность всех исходных столбцов/строк (кроме изменения alembic_version),
совпадение исходной схемы/данных с восстановленной копией и отсутствие изменений
источника. Сравнение выполняется хешированием значений, содержимое строк в отчёт
не выводится. Любая непройденная проверка даёт exit code 1; успех — 0.
Отчёт не заменяет снимки. Снимки содержат реальные данные/зашифрованные credentials:
хранить в закрытом каталоге, не коммитить. В Windows наследуется ACL каталога,
в POSIX создаётся каталог 0700. Рекомендуется `.deploy/` (исключён из git).

Для согласованной репетиции остановить writers источника. Если источник изменится
во время проверки, `source_unchanged=false`: такой результат не разрешает переход.
Инструмент никогда не заменяет исходную БД восстановленной копией и не переключает
процессы. При реальном откате после запуска новых writers нельзя терять принятые
команды: нужна отдельная процедура согласования данных.

## Принятие одного старого события

Применяется после schema upgrade и backup, до включения нового runtime.
Остановить старый/новый бот и worker: сервис защищает от новых общих команд,
но не может запретить запись старому процессу, обходящему этот слой.
Использовать отдельный тестовый бот/БД/Google-календарь для первого live-прогона.

`inspect` сверяет сохранённый `Meeting.google_event_id` в текущем binding.
Событие должно совпадать по ID, полному интервалу, названию и единственному email
клиента; иметь ETag и безопасную Meet-ссылку. Принимаются только confirmed,
rescheduled и reschedule_pending встречи с approved исходной заявкой.
Запрещены повторы/серии, all-day, прозрачные/отменённые события, чужие метки,
общий event ID у нескольких встреч и существующие Google outbox для этой встречи.
Неизвестные случаи требуют разбора, данные автоматически не исправляются.

Пример для изолированного тестового окружения; заменить демонстрационные пути,
Telegram ID и ID встречи на проверенные значения своего тестового процесса:

```powershell
.venv/Scripts/python.exe -m deploy.adopt_legacy_calendar inspect --database .deploy/test/planner.db --env-file .deploy/test/.env --owner-telegram-id 123456789 --environment meetly-test --meeting-id 1 --plan .deploy/adoption-1.json
```

План содержит ID встречи, версии, environment, хеши binding/содержимого и ETag,
без имени/email/токенов. Файл не перезаписывается. Сам inspect не создаёт sync
и не меняет событие; обновление истёкших OAuth-токенов возможно через GoogleTokens.
Проверить календарь и соответствие события встрече до применения плана:

```powershell
.venv/Scripts/python.exe -m deploy.adopt_legacy_calendar apply --database .deploy/test/planner.db --env-file .deploy/test/.env --owner-telegram-id 123456789 --environment meetly-test --plan .deploy/adoption-1.json
```

`apply` повторно проверяет доступ владельца по настроенному Telegram ID, версии,
хеши, событие и ETag. До сетевого PATCH сохраняет CalendarSync со state=adopting,
исходным event ID, интервалом и случайным токеном операции. Транзакция завершается
до сети. PATCH добавляет private meetly_environment/meeting_id/version/adoption_id,
сохраняя чужие private properties; время, описание, участники и конференция
в запрос не включаются. Используются If-Match и sendUpdates=none.
Это соответствует механизмам [private properties](https://developers.google.com/workspace/calendar/api/guides/extended-properties)
и [условных изменений по ETag](https://developers.google.com/workspace/calendar/api/guides/version-resources)
в Google Calendar; параметры уведомлений описаны в [Events.patch](https://developers.google.com/workspace/calendar/api/v3/reference/events/patch).

После проверки ответа sync получает applied_version и state=synced; ссылки
сохраняются в Meeting. Аудит записывает только действие/ID. Заявки, встречи,
их версии, переносы и уведомления не создаются; письма/Telegram не отправляются.
Старый pending-перенос с unknown previous_status остаётся таким же.

При потере ответа повторить `apply` с тем же планом: метка adoption_id должна
совпасть с сохранённым намерением. Уже принятую операцию повторно не патчим
и не дублируем аудит. При изменении локальных данных/версий нужен новый inspect;
при ETag conflict, несоответствии события или чужих метках — разбор до применения.
При частичном выполнении state=adopting сохраняется и блокирует изменение этой
встречи общими командами; worker не принимает такое состояние за готовую sync.
Не удалять это намерение автоматически: удалённая метка могла уже сохраниться.
Восстановление старого снимка БД не откатывает метки в Google. Если снимок не
содержит сохранённого adoption intent, повторное принятие такого события требует
отдельной сверки; чужие/неподтверждённые метки инструмент не присваивает.

Старое событие, которое не прошло adoption, нельзя молча пересоздать или отменить
через новый booking writer. Встреча с legacy event ID без подтверждённого sync
даёт CALENDAR_ADOPTION_REQUIRED; вся бизнес-команда откатывается. Старые pending
sync/outbox, созданные до этой процедуры, разбираются отдельно, не присваиваются
автоматически. Отменённые legacy-встречи/удалённые Google-события также требуют
отдельного разбора: инструмент не удаляет события и не восстанавливает их.

После принятия обычный outbox может переносить/отменять то же событие с сохранённым
ID, контролем версий, меток и ETag. Это не перенос событий между аккаунтами.
