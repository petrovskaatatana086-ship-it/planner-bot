# Google binding: границы проверки

Работа в dev. Изолированные временные SQLite, два независимых engine,
fake Google/Telegram. Рабочие .env/БД, Google, VPS и master не использовались.
Схема не меняется; runtime по умолчанию выключен.

Изменение календаря сохраняет результат, аудит и новую версию профиля одной
транзакцией. OAuth lifecycle использует отдельные короткие транзакции;
токены/state не включаются в OperationResult, payload hash или аудит.
State проверяется до exchange и повторно вместе с версией перед записью.

Проверяются:
- Конкурентный выбор одного календаря с одним ключом, replay после другой
  команды, stale version, подмена payload и блокировка владельца перед replay.
- Встречи, legacy event IDs, CalendarSync и Google outbox удерживают binding;
  same-calendar no-op не меняет версию и не переписывает существующий sync.
- Same-account reconnect сохраняет calendar ID и может сохранить refresh token.
- Другой аккаунт требует собственного refresh token и сбрасывает calendar ID,
  если смена разрешена. При существующих связях смена отклоняется атомарно.
- Ошибка reconnect и отказ провайдера не отключают активные токены.
- Старый/завершённый callback, неподходящий state и заблокированный owner
  отклоняются до сетевых вызовов, DB role не даёт полномочий владельца.
- Реальный callback сохраняет зашифрованные токены и потребляет state один раз;
  provider exception не попадает в текст HTTP/Telegram и сохраняемый error.
- Изменение настроек другим engine во время exchange возможно без writer-lock;
  результат старой версии не применяется. Новый OAuth flow во время сети
  не перезаписывается завершением или ошибкой прежнего callback.
- Реальный Telegram handler сохраняет только календарь с захваченной версией.

Первый целевой прогон: 14 тестов OK, 16.574с. Затем добавлены четыре проверки
Google outbox, blocked replay/reused key, provider denial и нового flow во время сети.
Полный регресс: **283 теста OK**, 199.082с, exit code 0.
Лог: full-google-binding-tests-2026-10-22.txt (объединённый вывод UTF-8).
git diff --check PASS. Предупреждения aiohttp о строковых app keys сохраняются.

Ограничения: сравнение аккаунтов по userinfo email (Google subject пока не хранится).
Переноса событий между аккаунтами/календарями нет: исторические sync тоже удерживают
binding до отдельной процедуры миграции. OAuth notification остаётся best-effort,
не booking outbox. FSM в памяти; после рестарта календарь выбирается заново.
Повтор уже завершённого OAuth callback возвращает 400, а не повторный обмен кода.
Live-проверка OAuth/прав календаря, legacy adoption, миграция на копии/restore
и отдельный серверный прогон остаются впереди.
