# Проверка занятости перед записью — 21.10.2026

Изменения: services/availability.py, интеграция snapshot в BookingCommands, freeBusy в GoogleEventGateway, tests/test_google_availability.py. Изменений схемы сверх ранее принятой 0008 нет. App.main/handlers не подключены к новому слою; production не обновлялся.

Итоговая проверка: полный unittest 156 тестов OK, лог full-availability-tests-2026-10-21.txt. Новые тесты: 23, включая сквозной сценарий с fake Google/Telegram/SMTP. Первоначальный отдельный прогон в availability-tests-2026-10-21.txt — 16 тестов; последующие проверки вошли в полный прогон.

Проверено:
- Google snapshot получает полный интервал и buffer до/после; равная точная граница перерыва разрешена;
- внешний частичный overlap запрещает запись, новая внешняя занятость до одобрения сохраняет pending;
- сеть не удерживает SQLite write-lock (другое подключение успешно пишет во время запроса);
- изменение calendar binding/настроек без legacy version bump требует нового snapshot;
- возраст ровно 5 секунд разрешён, 5 секунд + 1 мкс/будущее запрещены; повторов не более двух;
- локальная конкурирующая запись и blocked actor между preflight и commit не обходят проверки;
- независимые подключения с одинаковым свободным Google-слотом имеют одного локального победителя;
- replay не зависит от сети, включая commit другого подключения во время сетевого сбоя;
- ошибка сохранения Google-job откатывает Meeting, решение заявки, command result и уведомления;
- HTTP 200 с per-calendar errors, пропущенными полями, неправильным покрытием/offset/интервалом — отказ проверки;
- недопустимая локальная сетка отклоняется до Google;
- create → approve → CalendarSync/outbox → Google adapter → готовая ссылка клиенту, без повторного INSERT.

Все новые тесты используют временные файлы SQLite в workspace, явные синтетические настройки и поддельные API. Реальные credentials/календарь/письма не затрагивались.

Ограничения:
- freeBusy — снимок, не распределённая блокировка Google; ручная запись после проверки остаётся возможной внешней гонкой;
- snapshot реализован для новых заявок/подтверждения. Для переноса потребуется events.list с исключением своего event ID, полной пагинацией и обработкой recurring/all-day, без удаления всех пересечений на старом интервале;
- старые bot handlers не используют новые версии/транзакции; конкурентные гарантии относятся к новым командам, не к старому пути;
- UI/API, запуск worker из app.main и live-тестовое окружение остаются в плане этапа 4.
