# Управление доступом клиентов: границы проверки

Ветка dev, временные SQLite, fake Telegram. Рабочие .env, БД и сервер
не использовались. Схема не меняется, runtime остаётся opt-in.

Блокировка и разблокировка используют ProfileCommands.set_client_access.
Статус, OperationResult и аудит записываются одной SQLite-транзакцией.
Ключ Telegram-сообщения включает публичный bot ID, chat ID, message ID
и действие; секрет токена не сохраняется.

Проверки:
- Настроенный Telegram ID определяет владельца независимо от DB role.
- Заблокированный владелец не может выполнить даже replay принятой команды.
- Нельзя изменить доступ владельца или отсутствующего клиента.
- Повтор старой блокировки после разблокировки возвращает исходный результат,
  не применяя прежний статус снова. Ответ является результатом команды,
  а не новым чтением текущего статуса.
- Два engine с одним ключом создают один результат и одну запись аудита.
- Повтор ключа с другим содержимым отклоняется.
- Имя, email и сведения о согласии сохраняются при изменении доступа.
- Реальные обработчики Telegram вызывают общий слой; повтор сообщения после
  противоположного решения не меняет актуальный доступ.
