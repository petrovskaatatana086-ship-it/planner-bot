# Переносы, отмена и отказ — 21.10.2026

Полный unittest: 181 тест OK, 0 failures/errors. Лог full-reschedule-tests-2026-10-21.txt. Начальный отдельный набор — 22 теста в reschedule-tests-2026-10-21.txt; после добавления уведомления владельца и гонки approve/reject итоговый набор переносов — 24. Ещё один тест проверяет перенос legacy proposal при миграции 0009.

Реализованы общие клиентские/администраторские команды, RescheduleRequest/history, cancellation_reason, Google events.list для исключения собственного event ID и уведомления соответствующих бизнес-событий.

Проверено:
- предложение сохраняет старый интервал и длительность, не резервирует новый слот;
- занятый после предложения слот не согласуется; старая встреча и pending предложение сохраняются;
- отказ сохраняет предыдущий rescheduled и причину, отмена закрывает pending и освобождает старый слот;
- владелец может выполнить прямой перенос с superseded предыдущего предложения;
- повтор ключа не дублирует history/outbox, два подключения не создают два pending;
- approve против cancel переноса и approve против reject исходной заявки имеют одного победителя;
- чужой клиент получает NOT_FOUND; то же время и пустая причина отказа не принимаются;
- точная граница клиентской отмены 24 часа и отдельное право владельца проверены;
- отмена клиентом отдельно уведомляет владельца и не повторяется при replay;
- Google исключает точный event ID, оставляя чужое пересечение; events.list проходит все страницы, раскрывает recurring, интерпретирует all-day в часовом поясе календаря;
- metadata-only переход не запрашивает time-update invitation, перенос Google коалесцирует устаревшие задания, клиент получает новое время/ссылку;
- недоступность Google не отменяет локальную отмену уже связанной встречи; старый failed create не блокирует отменяющее задание;
- unique pending index проверен на уровне SQLite, миграция 0001–0009 выполняется реальными Alembic Operations.

Ограничения и миграция:
- все транспорты фальшивые; нет live Telegram/Google/SMTP операций и production deploy;
- новые команды/worker ещё не подключены к app.main/handlers; старые writers не получили их конкурентных гарантий;
- старый бот не сохранял previous_status при pending переносе: миграция переносит NULL, не угадывает. Новый отказ возвращает LEGACY_RESCHEDULE_REVIEW_REQUIRED, чтобы перед переключением сверить такие записи;
- немаркированные legacy Google events требуют отдельного принятия; синхронизация не перезаписывает чужие события;
- события Google и SQLite не образуют общую транзакцию; ручная внешняя запись после snapshot остаётся возможной гонкой;
- отсутствие sendUpdates при metadata-only запросе не является гарантией отсутствия всех писем со стороны Google.
