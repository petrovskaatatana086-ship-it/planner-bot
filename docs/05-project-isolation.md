## Правила для следующего проекта

1. Выделить уникальное имя Compose, например `new-project`, каталог `/opt/new-project`, собственные `.env`, `app.env`, `data` и резервные копии. Не использовать имена, пути и ключи соседнего приложения.
2. Скопировать шаблон `deploy/project-template/compose.yml` и `.env.example` в новый каталог (второй файл назвать `.env`). Указать реальный образ с фиксированной версией, UID/GID из образа, внутренний порт и свободный порт хоста. Подготовить `app.env` с настройками приложения, ограничить права файлов с секретами до `600`. Каталог `data` создать с владельцем UID/GID приложения. Приложение должно хранить постоянные данные в `/data`.
3. Проверить порт через `sudo ss -lntp` и конфигурации остальных проектов. Уже заняты: `8012` — бот, `3110` — planner, `3107` — checking; `22`, `80`, `443` — общие SSH/nginx. Порт `8013` в шаблоне является примером, а не резервированием.
4. Использовать собственную сеть Compose. Не задавать `network_mode: host`, `privileged`, Docker socket, общий `container_name`, чужие bind mounts или общую external-сеть. Базу нового приложения держать внутри его сети, без публикации порта на хост. Внутренние порты разных контейнеров могут совпадать.
5. Адаптировать шаблон к приложению: непривилегированный пользователь, запись только в явно разрешённые каталоги, собственный healthcheck. Шаблон рассчитан на HTTP-приложение с данными в `/data`; другие пути записи и дополнительные сервисы нужно описать явно.
6. Установить лимиты RAM, CPU, процессов, ротацию логов и резервное копирование. Перед запуском проверить `free -m`, `df -h /`, `sudo docker stats --no-stream`. На момент проверки у VPS 956 МиБ RAM, около 549 МиБ доступно, 3 ГБ свободного диска; значения меняются. Не выделять всю доступную память контейнерам: nginx, система и службы также используют её. Лимит RAM не ограничивает размер базы и bind-каталогов на диске.
7. Создать отдельный поддомен, отдельный nginx server-конфиг и сертификат. Проксировать только на выделенный `127.0.0.1:порт`; перед плавным reload выполнить `sudo nginx -t`. Сохранить прежний конфиг и проверить ответы соседних сайтов до и после изменения.
8. В новом каталоге выполнить `sudo docker compose config --quiet`, затем `sudo docker compose up -d`. Проверить `sudo docker compose ps`, healthcheck, HTTPS и сценарий приложения. Не выводить полный `docker compose config` в общие журналы: он может раскрыть секреты.
9. Обновлять и останавливать только свой проект из его каталога либо с явными `--project-name` и `-f`. Не применять глобальные `docker stop`, `docker system prune`, `docker volume prune` или удаление общих сетей. Для каждого проекта хранить план отката и проверенные резервные копии; не восстанавливать базу поверх работающего приложения.

Шаблон не подключён к работающему боту и не запускает новый контейнер автоматически. Для бота продолжать использовать существующий CI и `/etc/calendar-bot/compose.yml`; не запускать второй экземпляр с тем же токеном.

Отдельные сети, каталоги и лимиты предотвращают обычные конфликты проектов. Все контейнеры разделяют ядро, Docker daemon, диск и VPS; сбой хоста, заполнение диска или изменение общего nginx может затронуть несколько приложений. Если требуется строгая изоляция от недоверенного кода или независимость от отказа хоста, нужны отдельные виртуальные машины/VPS.
