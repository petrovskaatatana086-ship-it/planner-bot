# Планировщик встреч

Первый этап реализации Telegram-бота по `ТЗ.docx`.

## Что уже есть

- базовая структура Python-проекта;
- конфигурация через `.env`;
- определение владельца через `OWNER_TELEGRAM_ID`;
- создание таблиц БД при старте;
- модели `User` и `AuditLog`;
- Telegram-flow `/start`;
- регистрация клиента: согласие, имя, email, подтверждение;
- базовое меню клиента и владельца;
- команда `/admin` с серверной проверкой роли;
- создание заявки: дата, время, название, комментарий, проверка и отправка;
- список заявок клиента;
- список подтвержденных встреч клиента;
- просмотр новых заявок владельцем;
- подтверждение и отклонение заявки владельцем;
- профиль владельца `OwnerProfile`;
- настройки встреч: длительность, перерыв, лимит, горизонт, минимум до встречи;
- подготовка Google OAuth;
- модель `OAuthCredential`;
- кнопка «Google Calendar» для генерации ссылки подключения;
- миграции Alembic;
- простые тесты для email и назначения роли;
- email-уведомления клиенту: подтверждение, отказ, перенос и отмена встречи.

## Быстрый запуск локально

1. Создайте виртуальное окружение:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

2. Установите зависимости:

```powershell
pip install -r requirements.txt
```

3. Создайте `.env` на основе `.env.example` и укажите:

```env
BOT_TOKEN=токен_вашего_бота
OWNER_TELEGRAM_ID=ваш_telegram_id
DATABASE_URL=sqlite+aiosqlite:///./planner.db
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=bot@example.com
SMTP_PASSWORD=пароль_или_app_password
SMTP_FROM_EMAIL=bot@example.com
```

Если SMTP не заполнен, бот продолжит работать, но email-уведомления отправляться не будут.

4. Запустите бота:

```powershell
python -m app.main
```

## Проверка в Telegram

- Напишите боту `/start`.
- Если ваш Telegram ID равен `OWNER_TELEGRAM_ID`, бот должен открыть меню владельца.
- Если ID другой, бот начнет регистрацию клиента.
- Пройдите согласие, имя, email и подтверждение.
- После подтверждения должно открыться клиентское меню.
- Команда `/admin` для клиента должна ответить отказом.
- Нажмите «Записаться на встречу».
- Выберите дату из списка в формате `ДД.ММ.ГГГГ`.
- Выберите время в формате `ЧЧ:ММ`.
- Введите название встречи и комментарий.
- Отправьте «Отправить заявку».
- Владелец должен получить уведомление о новой заявке.
- Владелец может открыть «Новые заявки».
- Для подтверждения владелец отправляет `Подтвердить 1`.
- Для отклонения владелец отправляет `Отклонить 1`, затем причину.
- Владелец может открыть «Настройки встреч».
- Владелец может отправить `Длительность 90`, `Перерыв 15`, `Горизонт 30`,
  `Лимит 8`, `Минимум 24`, `Запись вкл` или `Запись выкл`.
- Владелец может нажать «Google Calendar».
- Если переменные Google не заполнены, бот покажет, чего не хватает.
- Если переменные заполнены, бот выдаст ссылку авторизации Google.
- Если SMTP заполнен, клиент должен получать email при подтверждении, отказе, переносе и отмене встречи.

## Техническая проверка

```powershell
python -m unittest discover -s tests
```

Также после запуска рядом появится файл `planner.db`, если используется SQLite.

## Миграции

Для новой базы можно применить миграции:

```powershell
python -m alembic upgrade head
```

На этапе разработки бот все еще умеет создавать таблицы при старте, чтобы первый
запуск был проще. Для сервера основной путь - Alembic.

## Google OAuth

Для генерации ссылки подключения Google Calendar нужны переменные:

```env
GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=
GOOGLE_REDIRECT_URI=
OAUTH_ENCRYPTION_KEY=
```

Ключ шифрования можно сгенерировать командой:

```powershell
python -c "from app.security import generate_encryption_key; print(generate_encryption_key())"
```

`GOOGLE_REDIRECT_URI` должен указывать на callback сервера:

```env
GOOGLE_REDIRECT_URI=https://your-domain.example.com/google/oauth/callback
```

При запуске `python -m app.main` вместе с ботом стартует HTTP-сервер:

```env
WEB_HOST=0.0.0.0
WEB_PORT=8000
```

## Email-уведомления

Для отправки писем нужны переменные:

```env
SMTP_HOST=
SMTP_PORT=587
SMTP_USERNAME=
SMTP_PASSWORD=
SMTP_FROM_EMAIL=
SMTP_FROM_NAME=Планировщик встреч
SMTP_USE_TLS=true
SMTP_USE_SSL=false
```

По умолчанию письма отправляются клиенту в сценариях:

- подтверждение заявки;
- отказ в заявке;
- перенос встречи;
- отклонение запроса на перенос;
- отмена встречи.

Если SMTP временно недоступен, бот не откатывает уже выполненное действие по заявке или встрече: письмо считается best-effort уведомлением.

На текущем шаге callback принимает `code` от Google, обменивает его на токены,
шифрует `access_token` и `refresh_token`, сохраняет их в `OAuthCredential` и
переводит Google-статус владельца в `active`.

После подключения Google Calendar:

1. Нажмите «Google Calendar».
2. Если статус активен, отправьте `Выбрать календарь Google`.
3. Бот получит список календарей владельца.
4. Отправьте номер календаря из списка.
5. Выбранный календарь сохранится в `OwnerProfile.calendar_id`.

После выбора календаря бот:

- учитывает занятость Google Calendar при показе свободных слотов;
- повторно проверяет занятость Google перед отправкой заявки;
- при подтверждении заявки создает событие Google Calendar;
- добавляет клиента как участника события;
- создает Google Meet-ссылку;
- сохраняет `google_event_id` и `google_meet_url` во встречу.

Перенос и отмена владельцем:

```text
Перенести 1 27.07.2026 10:00
Отменить встречу 1 Причина отмены
```

При переносе бот обновляет локальную встречу и Google Calendar Event. При отмене
бот отменяет Google Calendar Event и помечает встречу как отмененную.

Клиентский перенос и отмена:

```text
Запросить перенос 1 27.07.2026 10:00 Комментарий клиента
Согласовать перенос 1
Отклонить перенос 1 Причина отказа
Отменить мою встречу 1 Причина отмены
```

Клиентский перенос сначала получает статус `reschedule_pending`. Владелец должен
согласовать или отклонить запрос. Клиентская отмена работает только в разрешенный
срок до встречи.

Если `python -m venv .venv` падает в Windows-папке с кириллицей, используйте Docker
или создайте виртуальное окружение в проекте с латинским путем. Это ограничение
локального Python/Windows, а не кода бота.

## Что не входит в текущую реализацию

- мониторинг, резервное копирование и production-деплой.
- напоминания клиенту;
- фоновые задачи через Redis/worker;
- резервная отправка и повторные попытки уведомлений.
